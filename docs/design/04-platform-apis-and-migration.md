## Two consumer and command/search

Consumer 1 is a self-help purchase/accounting UI that looks at "how much to charge now, what costs will change depending on the amount of use, when it will open". Consumer 2 is an internal Sales/Support/Financial tool that looks at the source of the contract, Net30, the reasons for the change, the repair rights and the evidence. The two share a price and subscription contract, with the internal end receiving additional fields through authorized contracts/repair commands without bypassing the domain service DB.

## Compatibility rules (P02)

1. v1 response adds a selectable field that can be extended forward; The semantics of the mandatory fields, the units of the cents, the state meanings cannot be silently changed. The new charge type `components[]`, the predecessor of the well-known `kind`/`display_label`, states: If the old client can't understand the new pricing type, quote code `requires_client_capability`, check the declaration capability when accepted and refuse, not letting it blindfold. Don't pretend the new kind is a fixed charge.
2. The unknown enum value is a description of the general state and the server provided in a read-only image. For the command to create subscriptions or confirm amounts, the unknown value needs to fail closed. The old client cannot bypass the server quote by calculating the price itself or by ignoring the new line.
3. `PriceVersion`, `EntitlementPolicyVersion`, ContractVersion, meter schema, which are versions of each. Quote Exposing the results of the analysis with reference to the source; Any incompatible changes with `/v2` or new capabilities shall be negotiated. Contract testing for the old API client at least covers Basic/Pro, UNKNOWN, grace, contract quote, new component rejection and late to correct reading.
4. The delayed reading model must not be declared "open" to the client when the source has not yet been submitted; `pending` and the roundabout operation ID. Support can view source revision and provider observation to avoid finding caches when the end result is true.

## P03: Mature unit breakdown with price gray ADR

** Decision**: Account is certified, customer and organization identity; Commerce has price selection, assignment, rating, invoice, payment obligation and entitlement decisions. Initial Commerce call contracts with an existing adapter in the unit; There is only one writer per fact during the migration and no two systems can collect or validate invoices at the same time.

**Sequence**: First create source ID mapping and shadow quote/entitlement comparison, divided by tenant, plan, contract/no contract and older version cohort. In the meantime, we're going to have to make sure that we don't have shadow results. Fill in the historical assignment/invoice provenance and the missing data will be classified as discrepancy. Activate the new reading path with a small cohort with the feature flag to confirm delays and differences. Finally, each item hands over the command writer to Commerce, where the connection point has a unique owner record and playable outbox. Each step records p95 quote latency, variance rate, UNKNOWN downtime, reconciliation gaps and customer service events, setting the stop threshold, but the value threshold needs to be set after the baseline is reached.

** Reply**: Configuration/selection Stop selecting a new cohort when it is incorrect, no quotation is accepted and can be resubmitted; Received quote, sent provider operation, validated invoice not recalculated for return. The writer switches the new command and reconciliates it when it is incorrectly switched, and then switches it back after confirming the unresolved operation. It is not possible for the old writer to rebuild a capture on the same obligation. Migrate subscriptions to create new future assignments and audit decisions without changing v2 history.

** Cost**: shadow comparison, source mapping, dubbing and single writer coordination to increase short-term workload; In exchange, it will be possible to gradually dismantle accounts with Commerce, subject to historical accuracy verification. Documentation, capability consultation and visibility are the necessary delivery of product teams to the SKU, not a later addition.
